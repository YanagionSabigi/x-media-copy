# ezgif 优化器调研与 GIF 瘦身实测

2026-11-04。分支：`ezgif`。测试帖子：https://x.com/RaminNasibov/status/2117538582755729828 （`cat wave`，2026-11-03）。

## 结论

1. `Mad182/video-to-gif` 是 **编码器**（视频 → GIF），不是优化器；它是 ezgif.com 的默认编码器，站点还把它编译成了 WASM（`window.ezgifAssets.wasm["video-to-gif"]`）。ezgif.com 的 **`/optimize` 是另一套东西**，浏览器内跑的是 **Gifsicle WASM + Lossy GIF（有损 LZW）**。
2. 插件当前用 FFmpeg WASM 两遍 `palettegen/paletteuse`，并已启用 `+offsetting+transdiff` 差分帧。所以 **Gifsicle 的无损优化几乎没用**（`-O3` 只省 3.7%）；能大幅减体积的是 **有损 LZW + 降色 + 缩尺寸/抽帧**。
3. 按 ezgif 页面真实默认参数 `-O3 --lossy=30 --gamma=1`，该帖子普通点击的 GIF 从 **35.46 MiB 降到 15.29 MiB（-56.89%）**；再叠加 `--colors=128` 降到 **12.48 MiB（-64.82%）**。Alt 源帧率模式从 **146.86 MiB** 起步，是更值得先处理的问题。
4. 浏览器可用的 `gifsicle-wasm@1.96.4` 与本机 `gifsicle 1.97` 在相同参数下输出体积差 < 0.003%，因此上述结果可以直接平移到插件里，**无需上传媒体**。

## 1. 两个项目、两套机制

### 1.1 `Mad182/video-to-gif`（编码器）

单文件 `video-to-gif.cpp`，MIT，依赖 FFmpeg 的 libavformat/libavcodec/libavutil/libswscale。流水线：

```
解码 → 旋转元数据 → Lanczos 缩放 → 按目标 fps 选最近帧
→ delta frame（fuzz 差分）→ Wu 全局调色板量化（33³ 直方图，≤256 色）
→ Floyd–Steinberg 抖动 → 自实现 LZW → GIF89a
```

与体积直接相关的开关（源码默认值）：

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `-r FPS` | 10 | 输出帧数 `floor(duration*fps+0.5)`，上限 15000 帧 |
| `-w/-h/-maxw/-maxh` | 原尺寸 | 像素面积决定 LZW 输入量 |
| `-t TIME` | 全片 | 时长 × fps = 帧数 |
| `-fuzz N` | 2 | 与「已合成画布」比较时，RGB 各通道差 ≤N 视为未变化，差分子帧更小 |
| 全局调色板 | 256（有透明时 255） | 只生成一个全局表，帧内不写局部表 |
| disposal | delta 帧用 `1`（保留），整帧用 `2`（恢复背景） | 保证差分帧正确叠加 |

关键点：它比较的是 **合成画布** 而不是原始相邻帧，避免 fuzz 误差累积；无变化帧写成 1×1 透明像素；第一帧永远是完整画布。这套「delta + fuzz」就是仓库里自带的优化，不是 `/optimize` 页面那个优化器。

### 1.2 ezgif.com `/optimize`（优化器）

页面明确写着优化器「runs client-side with Gifsicle WASM」，底层是 [Gifsicle](https://www.lcdf.org/gifsicle/) 与 [Lossy GIF / giflossy](https://kornel.ski/lossygif)。`--lossy` 实现的是 **有损 LZW**：编码器不再找「完全匹配」的最长像素串，而是找「足够相似」的最长串，并用抖动掩盖误差；gifsicle ≥1.88 已把它并入主线，`gifsicle 1.97 --help` 里就有 `--lossy`。

从站点 `client-tool-optimize` JS 里读到的 **真实命令**：

| 页面选项 | 实际 gifsicle 参数 |
| --- | --- |
| Lossy GIF compression（默认，等级 30，范围 5–100） | `-O3 --lossy=30 --gamma=1 [ --colors N ] INPUT -o OUTPUT` |
| Color Reduction（默认 128） | `-O2 --colors 128 INPUT -o OUTPUT` |
| Remove every 2/3/4th frame | `-d<新延时> #<帧选择> -O2 -o OUTPUT` |
| Optimize Transparency | `-O3 INPUT -o OUTPUT` |
| Unoptimize / Coalesce | `--unoptimize INPUT -o OUTPUT` |

`--gamma=1` 不是可忽略的细节：它改变有损误差的色彩空间评估。同一份 GIF 上 `-O3 --lossy=30` 只省 19.94%，加上 `--gamma=1` 省 56.89%，但 SSIM 从 0.989 掉到 0.916（细噪点增多，肉眼在 400 px 宽下不明显）。

Gifsicle 的三个无损级别：`-O1` 只存变化矩形；`-O2` 额外用透明度；`-O3` 尝试多种方法取最小。空透明帧默认丢弃。`-O1` 用在已差分优化的 GIF 上反而会变大（本次 +10~12%）。

## 2. 插件现状

`gif.js` + `offscreen.js`：FFmpeg WASM（`@ffmpeg/core 0.12.10`，单线程）两遍转换。

| 模式 | 采样滤镜 | `paletteuse` | GIF flags |
| --- | --- | --- | --- |
| 直接点击（10 fps） | `fps=10,scale=w='min(800,iw)':h=-1:flags=lanczos` | `dither=bayer:bayer_scale=5:diff_mode=rectangle` | `+offsetting+transdiff` |
| 15 fps（旧任务） | 同上，fps=15 | `dither=sierra2_4a` | 默认 |
| Alt（source） | 无 | `dither=sierra2_4a` | 默认 |

输出上限 `-fs 256 MiB`，超时 10 分钟。当前已经具备 ezgif 编码器的等价手段：全局调色板、有序抖动、帧间矩形差分、宽度上限 800。缺的是 **优化器那一步的有损 LZW 与降色**。

## 3. 测试素材与方法

帖子媒体是 20 秒 H.264 视频（X 的「动图/视频」都不是真 GIF）。三条 MP4 变体：

| 分辨率 | 码率 | 字节 |
| --- | --- | --- |
| 396×270 | 256 kbps | 436,928 |
| 528×360 | 832 kbps | 1,231,948 |
| **1056×718** | **2176 kbps** | **3,363,430** |

`media.js` 的 `normalizeMedia()` 按 bitrate 降序取第一条，所以插件实际下载的是 **1056×718 / 2176 kbps**。本报告主表全部基于这一条；528×360 另做了一轮交叉验证。

- 基线：本机 FFmpeg 8.1.2 用 `gif.js` 导出的 `paletteArguments()` / `argumentsFor()` 原样执行（与 WASM 的 FFmpeg 6 版本不逐字节相同，见仓库既有记录 `docs/gif-optimization-2114222672704147600.md`；压缩率结论一致）。
- 优化：`gifsicle 1.97 win64`；浏览器可行性用 `gifsicle-wasm@1.96.4` 在同一输入上复核。
- 画质：FFmpeg `ssim` 对合成后的全部帧；另外导出 t=5s 帧做 2×2 目视对比。
- 所有媒体、脚本、原始 JSON 在 Git 忽略的 `test-results/ezgif-2117538582755729828/`。没有向 ezgif 上传任何文件。

## 4. 结果

### 4.1 插件当前输出（1056×718 源）

| 模式 | 尺寸 | 帧数 | 时长 | 字节 | MiB |
| --- | --- | ---: | ---: | ---: | ---: |
| 直接点击 10 fps | 800×544 | 200 | 20 s | 37,189,707 | 35.46 |
| Alt source 24 fps | 1056×718 | 480 | 20 s | 154,005,250 | 146.86 |

### 4.2 ezgif 真实参数，作用在 10 fps 基线上

| 配置 | 字节 | MiB | 减少 | SSIM |
| --- | ---: | ---: | ---: | ---: |
| 基线 | 37,189,707 | 35.46 | — | 1 |
| `-O3`（Optimize Transparency，无损） | 35,811,557 | 34.15 | 3.71% | 1.000 |
| `-O2 --colors 128`（Color Reduction） | 27,859,969 | 26.57 | 25.09% | 0.9845 |
| `-O3 --lossy=30`（不带 gamma） | 29,772,631 | 28.39 | 19.94% | 0.9891 |
| `-O3 --lossy=80 --colors=128` | 22,926,820 | 21.87 | 38.35% | 0.9674 |
| **`--gamma=1 -O3 --lossy=30`（ezgif 默认）** | **16,033,340** | **15.29** | **56.89%** | **0.9156** |
| ezgif 默认 + `--colors=128` | 13,082,551 | 12.48 | 64.82% | 0.9113 |
| `-O3 --lossy=80 --colors=64` | 17,292,585 | 16.49 | 53.50% | 0.9538 |
| `-O3 --lossy=80 --resize-fit 480x_` | 11,454,321 | 10.92 | 69.20% | — |

目视对比：四档在 400 px 宽的单帧上几乎看不出差别，SSIM 0.916 的差异主要是平坦区域的细噪点；这幅「猫浪」是大面积米色 + 黑色笔触，属有损 LZW 最不吃亏的一类画面。

**Alt 源帧率模式**：基线 154,005,250 字节（146.86 MiB，1056×718 / 480 帧）。`-O2/-O3` 无损只省 3.56%；ezgif 默认 `-O3 --lossy=30 --gamma=1` 降到 **63,194,306 字节（60.26 MiB，-58.97%）**。即便如此仍然偏大，说明源帧率模式更该先加帧率或尺寸上限，而不是只靠优化器。

### 4.3 交叉验证：528×360 变体（10 fps 基线 17,604,253 字节）

| 配置 | 字节 | 减少 | SSIM |
| --- | ---: | ---: | ---: |
| `-O3` | 17,088,574 | 2.93% | 1.000 |
| `-O3 --lossy=80` | 14,056,157 | 20.15% | 0.9889 |
| `-O3 --lossy=80 --colors=128` | 11,325,418 | 35.67% | 0.9741 |
| `-O3 --lossy=80 --colors=64` | 8,789,042 | 50.07% | 0.9597 |
| **ezgif 默认 `-O3 --lossy=30 --gamma=1`** | **8,584,244** | **51.24%** | **0.9318** |
| ezgif 默认 + `--colors=128` | 7,073,158 | 59.82% | 0.9261 |

`source`（24 fps）基线 44,794,219 字节上，`-O3` 只省 1.71%，`-O3 --lossy=30` 省 15.31%，`-O3 --lossy=80 --colors=64` 省 49.26%。**结论在 10/15/24 fps 三种帧率下都成立**：无损优化收益 < 4%，有损 LZW 是主要来源。

### 4.4 只调现有编码器参数（不引入新依赖）

同样从 1056×718 源出发，改 `palettegen=max_colors` 与 `scale` 宽度上限：

| 配置 | 字节 | MiB | 减少 |
| --- | ---: | ---: | ---: |
| 10 fps / 800 px / 256 色（现状） | 37,189,707 | 35.46 | — |
| 10 fps / 800 px / 128 色 | 30,809,908 | 29.38 | 17.15% |
| 10 fps / 800 px / 64 色 | 24,752,686 | 23.61 | 33.44% |
| 10 fps / **480 px** / 128 色 | 12,686,783 | 12.10 | 65.89% |
| 10 fps / **480 px** / 64 色 | 10,244,678 | 9.77 | 72.45% |

这条路径不需要任何新依赖、不需要新 WASM，只改 `gif.js` 里的 `max_colors` 与 `scale` 宽度上限；代价是分辨率和/或色数变化，属于重新编码而非无损重压缩。

（528×360 源的同类实测：`w400-k128` 9,386,565 字节 / -46.7%，`w400-k64` 7,616,140 字节 / -56.7%；叠加 `-O3 --lossy=80` 后最低 6,018,672 字节 / -65.8%。）

### 4.5 浏览器 WASM 可行性

| 输入 | 参数 | 原生 1.97 | WASM 1.96.4 | 差 |
| --- | --- | ---: | ---: | ---: |
| 10 fps 基线 | `-O3 --lossy=30 --gamma=1` | 16,033,340 | 16,032,885 | -0.0028% |
| 10 fps 基线 | 同上 + `--colors=128` | 13,082,551 | 13,082,793 | +0.0018% |

## 5. 建议

**先改 Alt 源帧率模式。** 146.86 MiB 的 GIF 已经接近 `-fs 256 MiB` 上限，且微信/QQ 等推送场景基本不可用。

推荐做成两级：

- **默认「瘦身」档**：`-O3 --lossy=30 --gamma=1`（ezgif 默认），体积约减 57%，画质肉眼可接受。
- **可选「更小」档**：追加 `--colors=128`，约减 65%；或 `--resize-fit 480x_` 约减 69%（会改尺寸）。
- 保留「原样」开关，因为部分画面（渐变、细纹理）对有损 LZW 敏感，且这是有损重编码，不是无损压缩。

两条落地路径：

**A. 只动 `gif.js`（零新依赖）**：把 `max_colors`、宽度上限、fps 做成可配置预设；用有序抖动 + 帧间矩形差分；不需要新 WASM，不触碰许可证。实测可到 -57% 左右，但属于「重新编码」而不是「重压缩」，参数变化会影响画面尺寸/帧率。

**B. 加 Gifsicle WASM 优化器阶段（与 ezgif 完全等价）**：

1. 把 `gifsicle-wasm` 的 `dist/gifsicle.js` (64 KB) + `dist/gifsicle.wasm` (237 KB) 放进 `vendor/gifsicle/`，在 `offscreen.html` 引入，或放进 Worker。
2. `offscreen.js` 在 `ffmpeg.readFile('output.gif')` 之后写入 WASM 虚拟 FS，执行
   `['gifsicle','-O3','--lossy=30','--gamma=1','/input.gif','-o','/output.gif']`，
   读回后校验尾字节 `0x3b`、帧数、时长与循环扩展，再生成 blob URL。
3. 失败时回退到未优化的原 GIF，保证不降低现有可用性。
4. 在 popup 增加「原样 / 瘦身 / 更小」三档，经 `storage` → `background.js` → `offscreen` 传参。

**落地前必须确认许可证**：`gifsicle-wasm@1.96.4` 的 `package.json` 声明 `GPL-2.0-only`，而本项目是 `GPL-3.0-or-later`。GPLv2-only 与 GPLv3 不能直接合并成一个衍生作品；若把它当作独立程序以 CLI 方式调用，仍属灰色地带。可选：向上游确认是否 `GPL-2.0-or-later`（gifsicle 源码常见写法是「version 2 or any later version」，但打包方标注为 only），或自行从源码按 GPLv2-or-later 编译 WASM，或改走方案 A。此外需同步更新 `vendor/NOTICE.md`、`vendor/upstream-components.json`、`vendor/source-manifest.json`、打包白名单与完整源码分发包。

## 6. 复现

```bash
# 基线（用 gif.js 导出的参数）
ffmpeg -v error -y -i input-1056x718.mp4 -vf \
  "fps=10,scale=w='min(800,iw)':h=-1:flags=lanczos,palettegen=stats_mode=full" \
  -frames:v 1 -update 1 palette.png
ffmpeg -v error -y -i input-1056x718.mp4 -i palette.png -lavfi \
  "[0:v:0]fps=10,scale=w='min(800,iw)':h=-1:flags=lanczos[s];[s][1:v:0]paletteuse=dither=bayer:bayer_scale=5:diff_mode=rectangle" \
  -an -fps_mode passthrough -gifflags +offsetting+transdiff -loop 0 baseline.gif

# ezgif 默认优化器
gifsicle -O3 --lossy=30 --gamma=1 baseline.gif -o optimized.gif
gifsicle -O3 --lossy=30 --gamma=1 --colors=128 baseline.gif -o optimized-small.gif
```

原始数据：`test-results/ezgif-2117538582755729828/native-results.json`、`hires-results.json`、`encoder-results.json`、`wasm-equivalence.json`、`post-metadata.json`，以及同目录各 `.gif` 样本与 `comparison.png`。

## 7. 限制

- 本机 FFmpeg 8.1.2 复现的是 `gif.js` 的**参数**，不是插件内 FFmpeg WASM 6 的逐字节输出；仓库既有记录已说明两者大小不同。优化器的**压缩比例**不受影响，因为它是纯 GIF → GIF 重压缩。
- 沙箱网络不能直连 `video.twimg.com`，三条 MP4 变体经公共只读代理取得，已用 `ffprobe` 校验为 24 fps / 20 s / 480 帧的完整 MP4。
- SSIM 是相对「当前基线 GIF」的结构相似度，不是相对原始视频；用于横向排序，不等于主观画质评分。
- 体积收益随画面内容变化；本片是大面积平色 + 硬边笔触，属于有损 LZW 收益较高的一类，渐变/噪点画面收益会明显下降。
